> 建立日期：2026-08-21（Asia/Shanghai）

## 1. 当前已确认事实

### 1.1 资料与模块接口

工作区已有以下本地资料，不需要再把 MLX90640 当成“无资料的未知模块”：

- `docs/参考资料/MLX90640-D110参考资料/MLX90640-EN.pdf`；
- `docs/参考资料/MLX90640-D110参考资料/原理图MLX90640_Thermal_Camera_SchDoc.pdf`；
- 同目录 `参考源码Mlx90640-thermal_camera.zip`，含 ESP32、Raspberry Pi 和 STM32 示例。

模块原理图给出的 4 针接口顺序为：

| 模组 P1 | 信号 |
|---:|---|
| 1 | SCL |
| 2 | SDA |
| 3 | GND |
| 4 | VCC / 3.3V |

原理图还显示外部/内部 I2C 两侧均有 4.7 kΩ 上拉，并通过双 N-MOS 做电平
转换；这意味着接到已有上拉的开发板总线后等效上拉会变小。接线后必须实测
SDA/SCL 空闲高电平、低电平和 400 kHz 上升沿，不能只根据标称电阻判断。

MLX90640 协议约束沿用已审计的官方资料边界：默认 7 位地址 `0x33`；供电
3.0~3.6 V；EEPROM 为 `0x2400..0x273f` 共 832 个 16-bit word；像素 RAM
`0x0400..0x06ff` 共 768 word，辅助区从 `0x0700` 开始；status/control 为
`0x8000/0x800d`。EEPROM 操作不超过 400 kHz。

### 1.2 开发板实际运行基线

2026-08-21 在当前 NFS 系统只读检查：

| Linux 总线 | OF node | 当前 client |
|---|---|---|
| `/dev/i2c-5` | `i2c@fead0000` | `0x14 gt911`、`0x22 fusb302`、`0x51 pcf8563` |
| `/dev/i2c-6` | `i2c@fec80000` | `0x14 gt911`、`0x22 fusb302`、`0x51 pcf8563` |

- 两条总线均已启用，当前都没有 `*-0033` I2C client，地址上无直接冲突。
- 运行 DT 的 I2C5/I2C6 均未显式设置 `clock-frequency`；RK3X I2C 驱动默认
  为 100 kHz。第一轮只读识别可先保持 100 kHz；EEPROM/RAM 性能验收再把
  选定总线显式设为 400 kHz并重编 DTB。
- 按底板 V1.2 原理图 PDF 的文字坐标与 JP5 pin 坐标逐行复核，I2C5 为
  JP5 pin 2=SCL、pin 4=SDA，I2C6 为 pin 6=SDA、pin 8=SCL；这些引脚右侧的
  `3.3V` 标注表示 GPIO I/O 电压域，不表示该针脚是 3.3V 电源输出。
- JP5 pin 10 是 `GPIO0_C6`，同样只是 3.3V I/O 域；当前基准 DTS 将该 GPIO
  用作 PCF8563 RTC 中断（`pcf8563_int`），严禁把它当作 MLX90640 VCC。
- MLX90640 模组供电应接板边 JP1（VOUT1）上明确标注的专用 `3.3V` 和 `GND` 针脚；JP2（VOUT2）是 `5V`，禁止用于 MLX90640。
  JP5 仅接 I2C5/6 信号。I2C2 为 JP5 pin 11=SDA、pin 13=SCL，属于 1.8V
  电平，不作为无额外电平转换的默认选择。JP5 这组 22 pin 扩展口自身没有
  标出的 GND pin，不能把相邻 GPIO 猜成地。
- 底板 V1.2 原理图标明 J12 pin 1 为 GND；仅当 JP2 不便使用、J12 未被风扇
  占用，且按实物 pin 1 标识用万用表确认与板地导通后，才可作为备用 GND。
- 当前 `CONFIG_VIDEO_I2C` 未启用，运行 DT 也没有 `melexis,mlx90640` 节点。
  因此板上尚无 MLX90640 驱动绑定或采集成功证据。

原始板端清单归档在：
`evidence/stage4/2026-08-21/mlx90640-p14-i2c-baseline.log`。

## 2. 现有参考实现不能直接照搬的原因

内核 `drivers/media/i2c/video-i2c.c` 已提供 MLX90640 参考路径，但当前实现存在
本项目必须验证/重构的语义问题：

1. `buffer_size=1664` 是 byte 数，而 `regmap_bulk_read()` 对 16-bit regmap 的
   `val_count` 是 value 数；直接把 1664 传入会把口径放大一倍。
2. nvmem callback 直接用 `0x2400 + byte_offset` 作为 16-bit register 地址，
   offset/bytes 与 word 地址的换算需要重新定义和实测。
3. 它从 `0x0400` 按软件定时读取，没有按 status new-data 位同步、清除 ready、
   保存 subpage ID，也没有验证 0/1 交替和 pair 时间语义。
4. 参考 ZIP 的 Raspberry Pi 代码一次读取 1664 bytes，并给 read message 加了
   `I2C_M_NOSTART`；本项目的 RK3X 路径应使用标准“两字节地址写 + repeated
   START + 分段读”，不依赖 `I2C_FUNC_NOSTART`。

因此 P1.4 先建立独立的原始传输事实，再决定 P1.5 是修正通用驱动还是实现
独立 `zzh` V4L2 Meta 驱动。不能把内核中已有参考文件计作个人完成成果。

## 3. 已准备的只读工具

权威源码：`tools/mlx90640_readonly_probe.c`。

该工具执行以下操作：

- 检查 adapter 支持 plain I2C transaction；
- 只读 `0x8000`、`0x800d`；
- 以 32 word/64 byte 分段完整读取两次 832-word EEPROM；
- 每段使用标准两 message repeated-start transaction，不使用 `I2C_M_NOSTART`；
- 比较两次 EEPROM，输出三个 ID word、耗时和 `EEPROM_MATCH`；
- 可选保存 1664-byte 大端 EEPROM 文件，供 `sha256sum` 和用户态算法使用。

它不会执行整总线地址扫描，不会写 status/control，也不会改 EEPROM。构建命令：

```sh
cd /rk3588_dev
prebuilts/gcc/linux-x86/aarch64/gcc-arm-10.3-2021.07-x86_64-aarch64-none-linux-gnu/bin/aarch64-none-linux-gnu-gcc \
  -O2 -Wall -Wextra -Werror \
  -o /tmp/mlx90640_readonly_probe \
  projects/rk3588_camera_bsp/tools/mlx90640_readonly_probe.c
```

交叉编译后的工具已经安装到 NFS RootFS 的
`/usr/local/sbin/mlx90640_readonly_probe`。确认接到 I2C5 后才在板上执行：

```sh
/usr/local/sbin/mlx90640_readonly_probe \
  /dev/i2c-5 /tmp/mlx90640-eeprom-be.bin
sha256sum /tmp/mlx90640-eeprom-be.bin
```

如果实物选择 I2C6，只替换为 `/dev/i2c-6`；不要同时在两条共享总线上盲试。

## 4. 实施顺序和通过门禁

### IV-A：实物与电气门禁

- 记录模组正反面、D110/BAA/BAB 丝印和 4 针线序照片。
- 断电接线；开发板 JP1（VOUT1）上明确标注的 `3.3V` 接模组 P1-4（VCC），JP1 上明确
  标注的 `GND` 接模组 P1-3；JP2（VOUT2）输出 5V，禁止接入。I2C5 选择 JP5 pin 4=SDA、pin 2=SCL；I2C6
  选择 pin 6=SDA、pin 8=SCL。不要把 JP5 pin 10（GPIO0_C6/RTC 中断）当作
  电源。针脚方向以实物丝印和底板 V1.2 原理图双重确认。
- 上电后测 3.3 V、空闲 SDA/SCL，不通过则不执行任何 I2C transaction。
- 第一版优先选一条总线并固定记录；当前建议沿用已审计命令的 I2C5，除非
  实物布线或波形表明 I2C6 更合适。

### IV-B：100 kHz 定点只读门禁

- 不运行 `i2cdetect -y`；只对已知 `0x33` 执行只读 probe。
- 连续运行工具至少 20 次，要求 20/20 成功、三组 ID word 稳定、每次两份
  EEPROM 完全一致且 SHA-256 稳定。
- 保存失败 errno、传输分段和耗时；NACK 不能解释成驱动缺失。

### IV-C：400 kHz EEPROM/RAM 门禁

- 在选定 I2C controller 节点显式增加 `clock-frequency = <400000>`，只构建
  kernel/DTB并用 `run nfsbootfdt` 验证；先检查同总线触摸、Type-C、RTC 回归。
- 逻辑分析仪确认实际频率、repeated-start、ACK/NACK、上升时间和单次传输时长。
- EEPROM 仍要求重复哈希一致；读取一次后缓存，不逐帧读取。
- 新增允许写 status/control 的原始帧工具前，先定义 ready 清除、失败重试和
  恢复策略；验证 8/16 Hz 的 subpage 0/1 交替、无重复/缺页。

P1.4 关闭条件是：电气证据完整、`0x33` 定点识别稳定、EEPROM 832 word 重复
哈希稳定、400 kHz 分段 RAM/aux/status/control 传输和 subpage 交替通过。只有
满足这些条件后才进入 P1.5 的 V4L2 Meta/VB2 ABI。
