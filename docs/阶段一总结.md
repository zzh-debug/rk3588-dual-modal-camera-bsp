# 阶段一总结：IMX415 硬件契约与 I2C 最小识别

## 1. 结论和验收边界

阶段一已完成代码、分项构建、网络部署和真实开发板 I2C 功能验证。
2026-08-02 21:58 至 22:03（Asia/Shanghai，时间取自开发环境；板端 RTC
当时未校时），ATK-DLRK3588 使用 TFTP 加载指定 Image/DTB，并通过 NFS
RootFS 启动。实验驱动在 `i2c3` 的 7 位地址 `0x1a` 连续完成 20 次
module remove/probe 循环，每次均读到寄存器 `0x311a = 0xe0`，验证脚本返回
`VERIFY_RC=0` 和 `STAGE1_RUNTIME_CHECK=PASS_CANDIDATE`。

本阶段的准确结论是：

- **IMX415 最小 I2C 功能门禁通过**：运行 DT、同地址节点隔离、MCLK/GPIO
  资源控制、I2C 寄存器读取、probe/remove 和 20 次重复绑定均有真实板端证据。
- `0x311a = 0xe0` 是 Rockchip/板卡厂商参考驱动使用的识别签名，**不是 Sony
  公开手册定义的芯片唯一 Chip ID**。简历、报告和面试均必须保留这个限定。
- 本次没有用示波器/逻辑分析仪测量 VCC3.3、AVDD/DOVDD/DVDD、MCLK、RESET、
  PWDN 和 I2C 波形，也没有保留实物连接器照片。因此可以进入下一阶段软件
  开发，但不能声称已完成“三路 Sensor 电源波形级严格时序验收”。
- 本阶段没有 mode 寄存器表、V4L2 Subdev、Controls、`s_stream()`、Media
  Graph、RKCIF 或 RKISP 功能；这些仍属于 P1.2/P1.3。

## 3. I2C 地址表示方式

```text
DTS reg / Linux i2c_client->addr: 0x1a
I2C bus write address byte:       0x34 = (0x1a << 1) | 0
I2C bus read address byte:        0x35 = (0x1a << 1) | 1
```

DTS 只能写 `reg = <0x1a>`；驱动将 `client->addr` 传给 I2C core，R/W 位由内核
根据 `i2c_msg.flags` 生成。将 `0x34` 写入 DTS 会把 8 位线上字节错当成 7 位地址。

## 4. 上下电时序

### 4.1 Sony 手册要求

1. 电源上升顺序为 `DVDD -> OVDD/DOVDD -> AVDD`，全部在 200 ms 内完成。
2. 电源稳定后 XCLR 保持低电平至少 500 ns。
3. XCLR 释放为高电平后，至少 1 us 后才出现 INCK 上升沿。
4. XCLR 释放后至少 20 us 才开始寄存器通信。
5. 断电顺序为 `AVDD -> OVDD/DOVDD -> DVDD`；OVDD 下降前，INCK、SDA、SCL、XCLR
   等应已无有效高电平。

### 4.2 阶段一驱动实现

```text
probe
  -> 以逻辑 1 断言低有效 PWDN 和 RESET/XCLR
  -> 若板级声明三路 regulator：DVDD -> DOVDD -> AVDD
  -> usleep_range(1000, 2000)
  -> 依次释放 PWDN 和 RESET/XCLR
  -> usleep_range(2, 5)
  -> 设置并使能 37.125 MHz MCLK
  -> usleep_range(20, 30)
  -> 读 0x311a
  -> 立即安全 power-off

power-off / rollback / remove
  -> 断言 RESET/XCLR 和 PWDN
  -> 关闭 MCLK
  -> 若可控：AVDD -> DOVDD -> DVDD 逆序关闭
```

本模组的三路 LDO 由连接器 3.3 V 本地生成且没有 enable 引脚，实验 DTS
因此不伪造 `dvdd-supply`/`dovdd-supply`/`avdd-supply`。驱动只在未来硬件完整
提供三路可控 regulator 时才执行 rail 开关，并拒绝只描述部分 rail。

板端循环后 `clk_summary` 显示 37.125 MHz、`enable=0`；模块卸载后该时钟的
prepare 计数从 1 回到 0，gpio-39/gpio-41 也从 debugfs 消失，重新加载后
恢复资源与驱动绑定。这证明软件 remove 释放路径生效，但不等价于物理
波形已测量。

## 5. 参考签名来源

Sony 公开数据手册的寄存器表将 `0x311a/0x311b` 定义为 `INCKSEL4`，
`0x311a` 的复位值为 `E0h`。公开手册没有给出 IMX415 唯一 Chip ID 寄存器。

当前 Rockchip 参考驱动 `kernel/drivers/media/i2c/imx415.c` 把 `0x311a`
命名为 `IMX415_REG_CHIP_ID`、期望值设为 `0xe0`，并留有 TODO 性质的厂商注释。
阶段一参考这两个数值，但在类型命名和日志中统一称为
`reference signature`，避免把厂商经验值写成 Sony 官方唯一 ID。

## 7. 关键代码流程

1. DT 在 `i2c3` 下实例化 `zzh,imx415-minimal@1a`，同时保留但禁用
   `sony,imx415@1a`，从数据源头防止同地址双占用。
2. I2C core 按 OF modalias 加载/绑定 `zzh_imx415_minimal`。
3. probe 检查 raw I2C 能力和 7 位地址，用 `devm_kzalloc()` 分配一个每设备私有上下文，
   用于保存 `i2c_client`、MCLK、RESET/PWDN descriptor、可选 regulator 及上电状态。
4. probe 获取 clock/GPIO/regulator，配置并检查 37.125 MHz MCLK，执行第 4 节的
   power-on 时序。
5. `zzh_imx415_read_reg()` 构造两个 `i2c_msg`：先写 16 位大端寄存器地址，
   再 repeated-start 读取 1 字节。不完整传输返回 `-EIO`，适配器负 errno 原样传递。
6. 读取失败或值非 `0xe0` 时返回错误，统一进入 power-off 回滚；命中后也立即
   power-off，所以 probe 成功并不意味着 Sensor 长期通电。
7. remove 再次执行幂等断电，devres 随设备解绑释放 clock/GPIO/regulator 句柄。

阶段一虽保留一个未调用的单寄存器写 helper 以完整表达 I2C 协议，但实际
probe 和验收脚本不写 Sensor 寄存器，也不运行 `i2cdetect`。

## 10. 本次网络启动故障的原因和恢复

### 10.1 现象链

1. U-Boot 中 `ping 192.168.5.10/192.168.5.11` 成功，Image 也能 TFTP 下载。
2. 同一会话下载 `atk_dlrk3588/rk3588-alientek-nfs.dtb` 返回
   `TFTP error: 'File not found' (1)`。
3. 继续启动后 Linux `root=PARTUUID=614e0000-0000`，根文件系统是
   `/dev/mmcblk0p6` 的 ext4，而不是 NFS。
4. Linux 中 `eth0` 取得 `169.254.173.88/16`，Ubuntu 无法 ping `192.168.5.20`。

### 10.2 根因

根因是 Ubuntu 宿主机上连接 SDK 部署目录与真实 TFTP/NFS 服务根的
bind mount 在重启后丢失：

```text
/home/zzh/workspace/rk3588_project/tftpboot/atk_dlrk3588
  -> /home/zzh/workspace/myproject/tftpboot/atk_dlrk3588

/home/zzh/workspace/rk3588_project/nfs_rootfs/atk_dlrk3588
  -> /home/zzh/workspace/myproject/nfs_rootfs/atk_dlrk3588
```

因此容器中的新 DTB 存在，但 TFTP daemon 当时看到的服务目录中没有它。
故障期间的直接 TFTP 回读已证明：服务端 Image 是另一个旧哈希
`03a997e1...4558287`，NFS DTB 则直接 `File Not Found`。

`nfsbootfdt` 当前的真实定义是：

```text
tftp ${kernel_addr_r} ${nfsimage};
tftp ${fdt_addr_r} ${nfsfdt};
booti ${kernel_addr_r} - ${fdt_addr_r}
```

分号表示无论上一条是否失败都继续下一条。第二次 TFTP 失败后，
`0x08300000` 仍保留 U-Boot 从 eMMC `resource.img` 读入的旧完整 DTB；`booti`
继续把该 DTB 传给 Linux。旧 DTB 中是 `root=PARTUUID=...`，所以 Linux 正常但
错误地回到了 eMMC RootFS。

U-Boot 中的 `ipaddr=192.168.5.20` 只属于 U-Boot 网络栈，不会自动传给 Linux。
eMMC Linux 没有收到 NFS DTB 中的静态 `ip=...`，最终使用 IPv4 link-local
`169.254.x.x`，因此 Ubuntu ping `192.168.5.20` 必然失败。

另外，U-Boot 网络栈是命令驱动/轮询式的：开发板执行 `ping` 或 `tftp`
时可以主动发包，但停在 U-Boot 提示符时不等价于 Linux 下的常驻 ICMP
应答服务。因此“U-Boot 能 ping Ubuntu，Ubuntu 持续 ping 不到停在提示符的
U-Boot”并不是单向物理网络故障。

串口上 `printenv nfsbootfdt` 中 `fdt_addr_r` 周边看似异常的大量空格是
终端换行/复制显示，不是本次根因。已刷源码定义是正确的
`${fdt_addr_r}`，且用户单独 `echo` 已读到 `0x08300000`；真实失败点是
TFTP 服务返回 `File not found`。

### 10.3 解决方法和当前证据

1. 在 Ubuntu 宿主机恢复 TFTP 和 NFS 两个服务目录的 bind mount。
2. 直接从 `192.168.5.11` 的 TFTP 服务回读 Image/DTB，核对大小和 SHA-256。
3. U-Boot 中重新下载两个文件，只在 DTB 下载成功后执行
   `booti 0x00400000 - 0x08300000`。
4. Linux 中用 `/proc/cmdline`、根挂载类型、`/etc/rootfs-source`、`eth0`
   地址和运行 DT 作五重确认。

修复后 TFTP 服务实际回读：


## 12. 遗留问题

1. 保留 J20 连接器、排线方向和模组版本照片，形成物理配置证据。
2. 用示波器测量 3.3 V、AVDD、DOVDD、DVDD、RESET、PWDN 和 37.125 MHz
   MCLK；如需审核 I2C repeated-start，再使用逻辑分析仪捕获。
3. 宿主机开机后检查两个 bind mount 和 `/etc/exports`，避免服务目录再次与容器部署
   目录脱节。
4. 后续单独立项修改 U-Boot `nfsbootfdt`，用 `&&` 防止 DTB 下载失败后继续启动；
   本次不修改原厂 bootcmd。
5. `0x311a = 0xe0` 不能排除其他兼容设备或复位状态恰好相同；P1.2 还需通过
   完整 mode 配置和真实出流继续增强型号/链路证据。

## 13. 原厂回退方法

最低风险回退是不改任何分区，重启后不打断默认 `bootcmd`，直接进入保留的
eMMC 原厂系统。当前阶段没有删除原厂驱动，也没有改写原厂启动命令。

网络启动 A/B 回退可使用不包含实验 DTSI 的原厂 1080x1920 DTB，或在 U-Boot
会话中使用从 `resource.img` 自动选中的原厂 DTB，保留 `sony,imx415`
和原厂 Media Graph。若需恢复源码默认路径，应从目标顶层 DTS 去掉实验
`#include`后只重编 kernel/DTB 并重新部署；不删除原厂
`kernel/drivers/media/i2c/imx415.c`，不清理或重置用户仓库。
