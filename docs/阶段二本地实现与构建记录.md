新增第三条隔离实现：

| 项目 | 阶段二实现 |
|---|---|
| OF compatible | `zzh,imx415` |
| 模块 | `zzh_imx415.ko` |
| 固定模式 | 3864x2192，SGBRG10，4 lane，线性 30 fps nominal |
| MCLK / lane rate | 37.125 MHz / 891 Mbit/s/lane |

## 2. 关键可靠性处理

- I2C 读使用 16 位地址 repeated-start 和 8 位数据；VMAX、SHR0、GAIN 按
  Sony 连续寄存器 little-byte order 写入。
- 每次批量表写保留第一处地址和错误，不吞掉短传输或部分写入。
- VMAX 和 SHR0 在一次 REGHOLD 中更新。修改 VBLANK 时同步保持 V4L2
  exposure 行数语义，并在 exposure 因新范围收敛时抑制递归旧时序写入。
- 电源、clock 和 regulator 使用逐项 enabled flag，power-on 中途失败进入统一
  逆序回滚；power-off 只有在单项 disable 成功后才清状态位。
- STREAMON 失败释放本轮 runtime PM 引用；STREAMOFF 的 standby I2C 错误向上
  返回，但仍释放 stream 引用，避免永久 usage counter 泄漏。
- endpoint probe 门禁要求恰好 4 lane 和唯一 445.5 MHz link frequency。
- 0x311A 只记录为 `vendor reference signature`，日志明确不是官方唯一 Chip ID。

## 7. 为什么本次没有声称完成部署

部署前执行 `findmnt -T`，两个服务目录都只解析到工作区根挂载：

```text
/rk3588_dev /dev/sda2[/home/zzh/workspace/rk3588_project] ext4
```

当前没有独立的：

```text
/rk3588_dev/tftpboot/atk_dlrk3588
/rk3588_dev/nfs_rootfs/atk_dlrk3588
```

bind mount，且容器内不可见宿主机 `/home/zzh/workspace/myproject`。因此当前
本地 `tftpboot` 中仍是阶段一旧网络 DTB，SHA-256 为
`c7049e...44de2c2`；RootFS 中也没有阶段二模块。若现在运行部署脚本，只会写
工作区普通目录，不能证明宿主机 TFTP/NFS 服务能看到新载荷，所以本次主动停止。

进一步检查发现 `.devcontainer/devcontainer.json` 当前只声明工作区 bind 和
Codex volume，没有声明 TFTP/NFS 服务目录。因此单纯 Reopen/Rebuild Container
不会自动保证这两个服务 mount 恢复。下一次部署前必须先在宿主机恢复原有 bind
机制，或明确把宿主机 `myproject/tftpboot`、`myproject/nfs_rootfs` 加入 Dev
Container mounts；在未确认宿主机真实目录和 Docker mount 结果前，本次不擅自
修改容器配置。

恢复 Dev Container 的两个 bind mount 后，必须先用 `findmnt -T` 看到各自独立
目标，再执行：

```bash
cd /rk3588_dev
./projects/scripts/deploy_net_boot.sh \
    -d rk3588-alientek-2mipi1080x1920-2hdmi \
    -m

KREL=$(cat kernel/include/config/kernel.release)
sudo install -D -m 0644 \
    projects/rk3588_camera_bsp/driver/zzh_imx415.ko \
    nfs_rootfs/atk_dlrk3588/lib/modules/$KREL/extra/zzh_imx415.ko
sudo install -D -m 0755 \
    projects/rk3588_camera_bsp/scripts/verify_imx415_stage2.sh \
    nfs_rootfs/atk_dlrk3588/usr/local/sbin/verify_imx415_stage2
sudo depmod -b nfs_rootfs/atk_dlrk3588 "$KREL"
```

注意：部署脚本的 `-m` 使用 `rsync --delete`，所以外部模块必须在脚本之后安装。
随后必须从宿主机真实 TFTP 服务路径或 TFTP client 回读 Image/DTB，并逐项比较
部署哈希，不能只对容器源文件求 hash。

## 8. 后续板端启动和最小验证

当前 U-Boot `nfsbootfdt` 仍用分号串联，DTB TFTP 失败后可能继续启动旧内存
内容。恢复服务并确认回读 hash 后，优先执行带 `&&` 的临时命令：

```text
printenv ipaddr serverip nfsimage nfsfdt kernel_addr_r fdt_addr_r
tftp ${kernel_addr_r} ${nfsimage} && tftp ${fdt_addr_r} ${nfsfdt} && booti ${kernel_addr_r} - ${fdt_addr_r}
```

Linux 启动后先确认环境，再运行 10 次候选检查：

```sh
cat /proc/cmdline
awk '$2 == "/" { print }' /proc/mounts
cat /etc/rootfs-source
ip -brief addr show eth0
modinfo zzh_imx415
verify_imx415_stage2 10
```

动态发现失败时，先保存 `media-ctl -p`，人工确认同一 graph 的 RKCIF node 后：

```sh
verify_imx415_stage2 10 /dev/videoX 12
```

首次 10 次通过后才扩大到 100 次。必须另外保存 Controls min/default/max 与
越界、VBLANK/曝光寄存器 readback、逐 Buffer sequence/timestamp、PM/clock/GPIO、
异常退出重开、原厂 A/B 和 minimal 回退证据。

## 9. 当前未验证事项

- 阶段二模块是否在真实板端 probe、0x311A 是否再次稳定读得 0xE0；
- Sensor async subdev 与当前 Rockchip graph 是否全部 notifier bind；
- D-PHY 是否实际使用 891 Mbps，RKCIF 是否得到有效 RAW10；
- 3864x2192 Sensor 与 3840x2160 Host crop 是否符合真实调用链；
- 30 fps、Bayer 顺序、前 8 帧稳定期和 RAW 数据有效性；
- VBLANK、EXPOSURE、GAIN 的实际寄存器行为和错误传播；
- runtime PM usage、MCLK/RESET/PWDN 以及 10/100 次启停资源守恒；
- 原厂 446 MHz 元数据路径与独立 445.5 MHz 路径的 A/B。

在上述真实板端证据完成前，只允许使用：

> 阶段二代码、本地编译及真实 TFTP/NFS 服务部署完成，待真机验证。
