### 3.1 为什么不沿用厂商 446 MHz

厂商驱动把 891 Mbit/s 模式映射到取整的 `446000000`。当前本地 D-PHY
在 `phy-rockchip-csi2-dphy.c:83-114` 查询 `V4L2_CID_LINK_FREQ`，
并用菜单值乘 2 得到 `data_rate_mbps`。Sony 公共表明确给出 891 Mbit/s，
因此阶段二使用精确一半 445.5 MHz，使 D-PHY 得到 891 Mbps。

当前 SDK 的 IMX334 驱动也对相同 891 Mbps 使用
`IMX334_LINK_FREQ_445 = 445500000`，属于本地兼容性旁证 [V]。

### 3.2 为什么不沿用厂商 `HMAX * 8`

厂商 mode 写 `HMAX=1100`，同时令
`hts_def = 1100 * 4 lanes * 2 = 8800`。若把 8800 与标准 CSI payload
`PIXEL_RATE=356.4M`、VMAX=2250 直接组合，只得到约 18 fps，与声明的
30 fps 不一致。

阶段二把三个概念分开：

1. `HMAX=1100` 是 Sony Sensor 内部 1H 时序寄存器 [D]；
2. `PIXEL_RATE=356.4M` 是 V4L2/CSI payload 元数据 [I]；
3. `HBLANK=1416` 使 V4L2 元数据满足 5280x2250x30 = 356.4M [I]。

HBLANK 在本阶段只读，不会反向改写 HMAX。最终帧率只以 [M] sequence/timestamp
为验收依据；若真机或 Host consumer 证明该语义不兼容，再以证据修订。

## 4. Selection 契约

| target | 返回矩形 | 理由 |
|---|---|---|
| `V4L2_SEL_TGT_NATIVE_SIZE` | 0,0 3864x2192 | [D][V] Sensor 实际输出 |
| `V4L2_SEL_TGT_CROP_BOUNDS` | 12,16 3840x2160 | [V] 当前 RKCIF/RKISP 明确查询此 target，并用它设 Host 输入 |
| `V4L2_SEL_TGT_CROP_DEFAULT` | 12,16 3840x2160 | [I] 固定居中有效区域 |
| `V4L2_SEL_TGT_CROP` | 12,16 3840x2160 | [I] 本阶段不可变当前 crop |

Rockchip 直接调用证据：

- `cif/capture.c:6310`、`capture.c:11339`；
- `cif/subdev-itf.c:195`、`subdev-itf.c:262`；
- `isp/rkisp.c:244-260`。

把 3840x2160 放在 `CROP_BOUNDS` 是当前 BSP 的兼容语义，不表示 Sensor
寄存器模式变成 3840x2160。阶段三必须分别保存 Sensor `get_fmt` 的
3864x2192 和 RKCIF/RKISP video node 的实际 3840x2160。

## 5. Controls 到寄存器的映射

| Control | 寄存器/算法 | 来源 | 写入策略 |
|---|---|---|---|
| `LINK_FREQ` | 445.5 MHz 单项菜单 | [D][I] | 只读，不写 I2C |
| `PIXEL_RATE` | 356.4 Mpixel/s | [I] | 只读，不写 I2C；RKISP 用它估算带宽 |
| `HBLANK` | 1416 | [I] | 只读，不写 HMAX |
| `VBLANK` | VMAX `0x3024..0x3026` | [D][V] | REGHOLD 下按 little-byte order 顺序写 |
| `EXPOSURE` | SHR0 = current VMAX - exposure；`0x3050..0x3052` | [D][V] | REGHOLD 下顺序写 |
| `ANALOGUE_GAIN` | GAIN_PCG_0 `0x3090..0x3091` | [D][V] | REGHOLD 下顺序写 |

Sony 说明 gain 是模拟加数字的总 PGC。为匹配 V4L2/Rockchip 既有接口，阶段二

## 8. 流和原子更新顺序

~~~text
STREAMON
  -> runtime PM resume / power_on
  -> STANDBY=1
  -> global table
  -> linear mode table
  -> REGHOLD=1
  -> VMAX / SHR0 / GAIN controls
  -> REGHOLD=0
  -> STANDBY=0

STREAMOFF
  -> STANDBY=1
  -> 即使 I2C 失败也释放 stream 持有的 PM 引用
  -> runtime power_off 断言 RESET/PWDN 并关闭 MCLK
~~~

Sony 打印页 64 说明 standby 取消后的前 8 帧是内部稳定期，第 9 帧起才是正常
图像。阶段二验证脚本记录这一限制；驱动不在 `s_stream()` 内睡眠 8 帧，
避免阻塞 Host 启动。正式图像判定应忽略初始稳定帧。

## 9. 尚未宣称的补充证据

1. mode 表关键寄存器 readback，至少 VMAX、HMAX、SYS_MODE、SHR0、GAIN、
   INCKSEL 和 MIPI timing；
2. 初始 8 帧稳定期对应的 RAW Bayer 图样和图像有效性；
3. 受控 stop-stream I2C 错误注入，以及示波器/逻辑分析仪的电源、MCLK、RESET、
   PWDN 波形；
4. 与原厂 446 MHz/厂商 HBLANK 元数据路径的相同负载 A/B。

上述内容是补充审计或阶段三输入，不改变本阶段已经完成的固定模式、Subdev、
Controls、runtime PM、Media graph 建立和 10/100 轮短流结论。

## 10. 2026-08-08 阶段二板端证据

使用新内建驱动和固定 1080x1920 NFS DTB 执行 `run nfsbootfdt` 后，板端确认：

- Linux `5.10.209 #4` 从 NFS RootFS 启动；
- `3-001a` 绑定 `zzh_imx415`，Sensor subdev 为 `/dev/v4l-subdev2`；
- Media graph 为 `zzh_imx415 3-001a -> dphy0 -> CSI2 -> stream_cif_mipi_id0`
  （RAW 节点 `/dev/video22`）；
- Subdev contract 为 `3864x2192 / SGBRG10 / 30 fps`，link frequency
  `445500000`，pixel rate `356400000`，居中 crop `3840x2160 at (12,16)`；
- 严格 10 轮和 100 轮短流全部通过，每帧 `10506240` bytes，实测约 30 fps；
- 运行时 PM 最终为 suspended，目标链路未出现 RKCIF 分配失败、CSI timeout、
  overflow、IOMMU fault、Oops 或 kernel panic。
