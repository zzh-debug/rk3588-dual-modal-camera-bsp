# 阶段二：IMX415 独立固定模式 Sensor 驱动与 V4L2 Subdev 实施计划

> 项目：基于 RK3588 的双模态成像 BSP 适配与采集链路可靠性开发  
> 平台：ATK-DLRK3588，Rockchip Linux 5.10.209  
> 计划日期：2026-08-06（Asia/Shanghai）  
> 当前状态：**阶段二目标路径已完成真实 TFTP/NFS 部署和板端验收；详见 `阶段二总结.md`**  
> 前置门禁：P1.1 最小 I2C 识别真机功能门禁已通过  
> 本阶段里程碑：P1.2  

## 1. 阶段决策

阶段二可以开始。阶段一已经取得以下进入条件：

- 独立 `zzh,imx415-minimal` 节点和最小驱动已在真实 J20 链路上绑定；
- 实验 DTB 中原厂同地址节点已禁用，运行时只有 `i2c3` 的
  `3-001a` 一个有效 client；
- NFS 网络启动、模块加载、20/20 次 remove/probe 和资源释放已经留存日志；
- 每次均读得厂商参考签名 `0x311A = 0xE0`；
- 原厂驱动、DTS、eMMC 启动和镜像回退路径仍然保留。

阶段一仍缺连接器照片和电源、MCLK、RESET/PWDN 物理波形。它们限制的是
“严格硬件时序已完成实测”这一表述，不阻塞阶段二软件实现；在最终对外验收前
仍必须补齐。

阶段二不直接进入 RKCIF Host 可靠性修改，也不把原厂 IMX415 已有出流能力计为
个人成果。正确顺序是先完成独立 Sensor 驱动的单一固定模式、V4L2 Subdev、
Controls 和 runtime PM，再进入阶段三的正式 Media Graph、RKCIF RAW 与 RKISP
NV12 验收。

## 3. 冻结目标和非目标

### 3.1 唯一固定模式

| 属性 | 阶段二目标 | 证据边界 |
|---|---|---|
| 输出尺寸 | 3864x2192 | 厂商驱动固定模式定义；不是 3840x2160 Sensor 原生 mode |
| Media Bus Code | `MEDIA_BUS_FMT_SGBRG10_1X10` | 厂商实现与当前模组参考路径 |
| Bayer 顺序 | GBRG RAW10 | 必须由 RAW 图样/色彩结果继续验证 |
| CSI-2 lanes | 4 lanes | 开发板 DTS 与模组连接 |
| 帧率 | 30 fps | 厂商模式声明；阶段二必须用真实时间戳测量 |
| MCLK | 37.125 MHz | 阶段一硬件契约与厂商模式 |
| lane rate | 约 891 Mbit/s/lane | 厂商模式命名和参考实现 |
| HDR | 关闭，线性模式 | 本阶段只做 `NO_HDR` |
| 虚拟通道 | VC0 | 单线性曝光 |

直接源码证据位于：

- `kernel/drivers/media/i2c/imx415.c:457`：
  `imx415_global_10bit_3864x2192_regs`；
- `kernel/drivers/media/i2c/imx415.c:649`：
  `imx415_linear_10bit_3864x2192_891M_regs`；
- `kernel/drivers/media/i2c/imx415.c:1079`：3864x2192、RAW10、30 fps、
  VMAX/HMAX、37.125 MHz 和 4-lane 模式描述。

上述位置只证明厂商参考实现如何配置，不等于 Sony 公共手册公开了所有寄存器。

### 3.2 本阶段必须实现

- 新驱动 `zzh_imx415.c`，匹配 `compatible = "zzh,imx415"`；
- 16 位寄存器地址、8 位寄存器值的 I2C 读写和批量表写入；
- 严格 power-on/off、参考签名校验、probe 错误逆序回滚；
- 单一 3864x2192 RAW10 30 fps mode 和 standby/stream 切换；
- V4L2 Subdev、一个 source pad、mbus code/size/interval 枚举；
- TRY/ACTIVE format、只读或明确定义的 selection 语义；
- `LINK_FREQ`、`PIXEL_RATE`、只读 `HBLANK`、
  `VBLANK`、`EXPOSURE`、`ANALOGUE_GAIN`；
- VBLANK 改变时动态收敛 exposure 上限；
- runtime PM、并发状态保护、启动/停流失败回滚和 remove 释放；
- 独立 Kconfig/Makefile、实验 DTSI、自动验证脚本、寄存器来源台账和注释版镜像；
- 与原厂路径和阶段一最小识别路径进行可回退 A/B。

### 3.3 明确不做

- HDR2/HDR3、12-bit、2-lane、1932x1096 或 binning mode；
- HFLIP/VFLIP；翻转会改变 Bayer 顺序，本阶段不在语义未审计时暴露；
- thunderboot、camera sleep/wakeup 和批量 Rockchip 私有 ioctl；
- IQ/3A、RKAIQ 或 ISP 调参；
- RKCIF IRQ/DMA/VB2 源码修改；
- RKISP 源码修改；
- Host 自动恢复、frame timeout、`vb2_queue_error()` 和 workqueue；
- 300/3000 帧正式 RAW 验收、8 小时长稳或 1000 次启停；
- MLX90640、LED 或项目二用户态功能。

这些内容不是取消，而是分别留给 P1.3 及后续阶段，避免把 Sensor 驱动问题、
Media Graph 问题和 Host 可靠性问题混在一次改动中。

## 5. 分门槛实施顺序

### II-0：寄存器来源与部署基线冻结

代码实现前先完成以下审计：

1. 只抽取厂商驱动的 3864x2192 RAW10 全局表和 891M 线性表；
2. 给每个寄存器标注来源、用途、写入阶段和是否能从公开手册验证；
3. 审计 `LINK_FREQ`、`PIXEL_RATE`、HMAX/VMAX 与 HBLANK 的
   对外语义，不直接照抄相互矛盾的元数据；
4. 追踪 RKCIF/RKISP 对 selection target 的实际调用，再冻结
   `NATIVE_SIZE`、`CROP_BOUNDS`、`CROP_DEFAULT`；
5. 保存阶段一 Image、DTB、模块、运行 DT 和原厂回退 DTB 的 hash；
6. 核实宿主机 TFTP/NFS bind mount、TFTP 实际回读和 NFS export。

II-0 退出条件：

- `阶段二寄存器来源台账.md` 第一版完成；
- 四项元数据问题有明确结论或被显式列为待真机测量，不能含糊带入代码；
- 阶段一和原厂回退载荷均可定位；
- 未修改 Sensor/Host 源码。

### II-A：单固定模式和 `s_stream()`

实现：

- 自有数据结构、资源获取和 I2C helpers；
- 单 mode 描述，不建立多模式抽象需求；
- 独立组织的全局表与 mode 表，仅必要寄存器携带厂商来源说明；
- probe 时上电、参考签名检查、注册 Subdev 后允许 runtime idle；
- start stream：取 PM 引用、写全局表、写 mode 表、应用 Controls、退出 standby；
- stop stream：写 standby，保留错误返回，再释放 PM 引用；
- 一个 MEDIA_PAD_FL_SOURCE pad 和最小 Subdev 注册。

II-A 真机门槛：

- probe/reference-signature 日志正确；
- media entity 能被发现；
- 通过现有 J20 Host 图做短时 RAW smoke，仅用于证明 `s_stream()` 被调用并
  产生数据；
- 10 次短 STREAMON/OFF，无 I2C 错误、无引用泄漏、无无法重开。

这次短流不是阶段三正式 Media Graph 或 RKCIF RAW 验收。

### II-B：V4L2 Subdev 格式、selection 和 Controls

实现和验证：

- `enum_mbus_code` 只返回 `SGBRG10_1X10`；
- `enum_frame_size` 只返回 3864x2192；
- `enum_frame_interval` 只返回 30 fps；
- TRY format 不改变 ACTIVE 状态；
- 不支持的 code/size 按冻结规则收敛或返回错误，并通过测试固定行为；
- selection 明确区分 3864x2192 Sensor 输出与居中 3840x2160 有效区域；
- Controls 的 min/max/step/default 与寄存器宽度、VMAX/HMAX 一致；
- 运行中修改 exposure、gain、VBLANK 能产生预期寄存器写入；
- 越界值由 V4L2 control core 拒绝；
- VBLANK 改变后 exposure 最大值同步更新。

II-B 退出条件是 API 和实际寄存器行为均有日志，不能只证明
`v4l2-ctl --list-ctrls` 能看到名字。

### II-C：runtime PM、并发和错误路径

设计方向：

- 使用本内核已有的 `pm_runtime_resume_and_get()`；
- `runtime_resume()` 只调用统一 `power_on()`；
- `runtime_suspend()` 只调用统一 `power_off()`；
- stream ON 成功后持有 PM 引用，失败时逆序释放；
- stream OFF 先尝试 standby，再释放 PM 引用，并让 I2C 错误对调用者可见；
- `powered`、`streaming` 只在硬件动作成功后更新；
- mutex 不跨会回调自身的 PM 边界，避免 PM callback/mutex 自锁；
- remove 先注销 Subdev/entity/controls，再完成 PM disable 和最终断电。

必须覆盖的故障点：

- clock rate 设置失败或 clock enable 失败；
- regulator enable 中途失败；
- RESET/PWDN 后 I2C 不应答；
- 全局表或 mode 表写入中途失败；
- control setup 失败；
- 退出 standby 失败；
- stop-stream standby 写失败；
- 用户态 SIGTERM/SIGKILL 后关闭并重开；
- remove 时处于 idle 和 active 两种状态。

II-C 真机门槛：

- 100 次短 STREAMON/OFF；
- 每轮 sequence、timestamp 和错误码可追踪；
- 前后 clock、PM usage、fd、slab/CMA 无持续增长；
- 异常退出后设备可正常关闭、重开并再次出流。

### II-D：阶段收口和原厂 A/B

在相同硬件、同一 1080x1920 屏幕 DTB 基线和相同短流负载下，对比：

- 自研 `zzh,imx415`；
- 原厂 `sony,imx415`；
- 必要时回退到 `zzh,imx415-minimal` 复核电气/I2C。

保存代码 diff、构建日志、载荷 hash、TFTP 回读 hash、完整启动日志、
运行 DT、media graph、Controls、短流 CSV、PM/资源数据和 A/B 结果。

II-0 至 II-D 的主路径门禁已经通过真实板端验证，正式结论见
`docs/阶段二总结.md`。寄存器逐项 readback、物理波形和原厂同负载 A/B 属于
补充审计项，不能写成已经取得的证据：

> 阶段二固定模式/Subdev/Controls/runtime PM 真机验收通过；阶段三正式 RAW/NV12
> 和补充硬件证据另行记录。

## 6. 驱动结构和关键流程

### 6.1 核心状态

阶段二驱动私有结构至少需要：

| 成员类别 | 用途 |
|---|---|
| `i2c_client *` | I2C 传输和设备日志 |
| `clk *xvclk` | 37.125 MHz MCLK |
| RESET/PWDN GPIO descriptors | 逻辑值遵循 DTS 的 active-low 描述 |
| optional AVDD/DOVDD/DVDD regulators | 兼容有独立电源描述的硬件；当前模组由 3.3 V 本地 LDO 生成 |
| `v4l2_subdev`、`media_pad` | Sensor entity 和唯一 source pad |
| `v4l2_ctrl_handler` 及 control pointers | 元数据和运行时寄存器控制 |
| `mutex` | 保护 ACTIVE format、Controls 与 streaming 状态 |
| 当前 mode/format | 即使只有一个 mode，也明确 TRY/ACTIVE 状态边界 |
| `powered`、`streaming` | 软件状态；只在硬件动作成功后提交 |

所有主结构和 controls 使用 `devm_kzalloc()` 或框架自有生命周期，
mode/寄存器表使用只读静态存储，不为固定表动态申请内存。每一处分配和所有权
必须在注释版说明，避免 remove 时重复释放或漏释放。

### 6.2 probe 流程

~~~text
匹配 compatible
  -> 分配私有结构并初始化 mutex
  -> 获取 clock/GPIO/optional regulator
  -> 解析并校验 endpoint（4 lanes、link frequencies）
  -> 初始化唯一 mode、pad、Subdev 和 Controls
  -> 临时 power_on
  -> 读取 0x311A 厂商参考签名
  -> 注册 async Sensor Subdev
  -> 配置 runtime PM 并进入 idle
~~~

任一步失败都按实际完成顺序逆序回滚。设备尚未注册时不能走依赖已注册 entity
的清理路径，设备已经进入 runtime PM 后不能再手工重复断电。

### 6.3 start/stop 流程

~~~text
STREAMON
  -> 已 streaming 则幂等返回
  -> pm_runtime_resume_and_get()
  -> 写 global table
  -> 写 3864x2192 RAW10 mode table
  -> v4l2_ctrl_handler_setup()
  -> 0x3000 bit0 = 0，退出 standby
  -> streaming = true

STREAMOFF
  -> 未 streaming 则幂等返回
  -> 0x3000 bit0 = 1，进入 standby
  -> streaming = false（仅在状态处理规则满足后提交）
  -> pm_runtime_put()
  -> 向上保留 stop I2C 错误
~~~

对 stop 写失败时“软件是否仍视为 streaming”的策略必须在 II-C 编码前冻结；
无论选择哪种策略，都不能吞掉错误，也不能遗失 PM 引用。

## 7. 寄存器来源纪律

来源台账统一使用：

| 标记 | 含义 |
|---|---|
| [D] | Sony 公共数据手册可直接核对 |
| [V] | Rockchip/模组厂商参考驱动或 DTS |
| [M] | 当前开发板 I2C readback、示波器、逻辑分析仪或帧数据实测 |
| [I] | 根据时序、接口规范或代码调用关系作出的工程推断 |

台账每行至少记录：地址、位宽、写值/范围、功能、写入阶段、来源标记、原始页码或
源码位置、是否完成板端 readback，以及错误值的风险。

公共 Sony 产品资料没有公开全部推荐寄存器。因此允许仅对必要固定 mode 表使用
带 [V] 标记的厂商值，但必须满足：

- 新驱动的结构、状态机、V4L2 API、PM 和错误路径独立设计；
- 不复制原厂整文件后批量改符号；
- 不携带 HDR、12-bit、2-lane、thunderboot 等无关数组；
- 不把 [V] 寄存器描述成“由 Sony 手册独立推导”；
- `0x311A = 0xE0` 始终称“厂商参考签名”，不称 Sony 官方唯一 Chip ID。

## 8. II-0 必须回答的四个元数据问题

### 8.1 `LINK_FREQ`

名义 lane rate 约 891 Mbit/s，DDR 对应 link clock 理论值为 445.5 MHz；厂商驱动
对 V4L2 暴露取整的 446 MHz。编码前要追踪 Rockchip consumer 是要求精确时钟、
标准菜单值还是 BSP 兼容值，再选择 445.5 MHz 或 446 MHz，并在台账记录理由。

### 8.2 `PIXEL_RATE`

候选 CSI payload 公式：

~~~text
pixel_rate = link_freq * 2 * 4 lanes / 10 bits
~~~

445.5 MHz 对应 356.4 Mpixel/s，446 MHz 对应 356.8 Mpixel/s。这个 control 是
链路负载元数据，不能直接等同于 Sensor 内部 HMAX/VMAX 使用的时序时钟。

### 8.3 HMAX、HBLANK 和帧率

厂商固定模式写 `HMAX = 0x044C = 1100`、`VMAX = 0x08CA = 2250`，
但 `hts_def = HMAX * 4 lanes * 2` 与 CSI pixel-rate 直接组合时不能得到
直观一致的 30 fps。必须分开说明：

- Sensor 寄存器 HMAX/VMAX 的行、帧时序；
- V4L2 `HBLANK` control 对用户空间的元数据语义；
- 用 Buffer `CLOCK_MONOTONIC` 时间戳测得的实际帧间隔。

在三者未理顺前，不盲目复制 `hts_def`。

### 8.4 selection

厂商代码对 3864x2192 输出返回居中 3840x2160 区域：

~~~text
left = 12, top = 16, width = 3840, height = 2160
~~~

当前实现将它放在 `V4L2_SEL_TGT_CROP_BOUNDS`。II-0 要追踪 RKCIF/RKISP
实际查询哪个 target，再决定 `NATIVE_SIZE`、`CROP_BOUNDS` 和
`CROP_DEFAULT`，避免为了兼容厂商调用而错误宣称 Sensor 输出就是 4K UHD。

## 9. DTS 和 Media Graph 边界

阶段二 DTSI 应：

- 禁用原厂 `&imx415`；
- 不启用阶段一 `zzh_imx415_minimal`；
- 在 `&i2c3` 建立唯一 `zzh,imx415` 节点；
- 沿用已审计的 J20 clock、GPIO、power-domain、4-lane endpoint 电气连接；
- 只启用调用 Sensor `s_stream()` 所必需的现有 D-PHY/CSI/RKCIF Host 节点；
- 不修改 RKCIF/RKISP 驱动源码，不在本阶段宣称完成 Host/ISP 适配。

阶段二可使用现有 J20 Host 图做短 RAW smoke，因为没有 Host pipeline 就无法从
video node 驱动 Subdev 的 `s_stream()`。这只是 Sensor 固定 mode 的证据。

以下正式验收留到阶段三：

- 从 Sensor endpoint 到 D-PHY、CSI2、RKCIF、SDITF、RKISP 的逐端点审计；
- RKCIF RAW 格式、stride、sizeimage、sequence、timestamp 的 300/3000 帧测试；
- RKISP 3840x2160 NV12 和 IQ/色彩结果；
- Media Graph A/B、长流、错误计数和重复启停。

## 10. 构建、部署和启动计划

阶段二只做 kernel 分项构建和独立外置模块构建，不全量构建、不刷整机、
不修改原厂 `bootcmd`。

Dev Container 内使用普通 `vscode` 用户：

~~~bash
cd /rk3588_dev
./build.sh kernel

KERNEL_CROSS=/rk3588_dev/prebuilts/gcc/linux-x86/aarch64/gcc-arm-10.3-2021.07-x86_64-aarch64-none-linux-gnu/bin/aarch64-none-linux-gnu-
make -C /rk3588_dev/kernel \
    M=/rk3588_dev/projects/rk3588_camera_bsp/driver \
    ARCH=arm64 \
    CROSS_COMPILE="$KERNEL_CROSS" \
    CONFIG_VIDEO_ZZH_IMX415_MINIMAL=m \
    CONFIG_VIDEO_ZZH_IMX415=m \
    modules

./projects/scripts/deploy_net_boot.sh \
    -d rk3588-alientek-2mipi1080x1920-2hdmi \
    -m
~~~

部署脚本的 `-m` 路径会用 `rsync --delete` 同步内核模块目录，
所以外置模块必须在它之后安装：

~~~bash
KREL=$(cat kernel/include/config/kernel.release)
sudo install -D -m 0644 \
    projects/rk3588_camera_bsp/driver/zzh_imx415.ko \
    nfs_rootfs/atk_dlrk3588/lib/modules/$KREL/extra/zzh_imx415.ko
sudo depmod -b nfs_rootfs/atk_dlrk3588 "$KREL"
~~~

`sudo` 只用于保持 NFS RootFS 属主，不用于编译。

每次板测前必须：

1. 检查宿主机 TFTP/NFS bind mount 在重启后仍存在；
2. 从真实 TFTP 服务端路径读回 Image 和 DTB；
3. 将读回 SHA-256 与容器部署文件比较；
4. 确认 NFS export 指向宿主机
   `/home/zzh/workspace/myproject/nfs_rootfs/atk_dlrk3588`；
5. 确认 RootFS 中模块 vermagic 和 hash。

当前 U-Boot `nfsbootfdt` 仍用分号串联，DTB 下载失败后可能继续用旧内存
内容启动。在另行修复 U-Boot 前，板测优先手工使用：

~~~text
tftp ${kernel_addr_r} ${nfsimage} && tftp ${fdt_addr_r} ${nfsfdt} && booti ${kernel_addr_r} - ${fdt_addr_r}
~~~

`Fdt Ramdisk skip relocation` 不能证明新 DTB 已成功下载。

## 11. 真机验证与证据清单

验证脚本必须动态发现 media device、Sensor subdev 和 RKCIF video node，不把
`/dev/media0`、`/dev/v4l-subdev0` 或 `/dev/video0` 写死。

每轮至少归档：

- 源码 diff、Git 状态、编译器、kernel release 和模块 vermagic；
- kernel/module 构建完整日志；
- Image、DTB、模块的部署 hash 和 TFTP 实际回读 hash；
- U-Boot 两次 TFTP 成功输出和完整 Linux 串口启动日志；
- `/proc/cmdline`、NFS 根挂载、`/etc/rootfs-source`；
- 运行 DT compatible/status、I2C client 和绑定 driver；
- `media-ctl -p`、`v4l2-ctl --list-devices`；
- mbus code、size、interval、TRY/ACTIVE format 和 selection 日志；
- Controls 的 min/default/max、越界行为和寄存器 readback；
- VBLANK 改变前后 exposure range；
- 10 次和 100 次短流 CSV，含开始时间、结束时间、帧数、sequence gap、
  timestamp delta、退出码和 dmesg 增量；
- runtime PM status/usage、clock enable count、GPIO 状态；
- 测试前后 fd、slab、CMA 和内核告警；
- SIGTERM/SIGKILL 后关闭、重开和再次出流；
- 原厂/eMMC A/B 和阶段一 minimal 回退证据。

格式、bytesused/sizeimage、帧数、sequence、timestamp 和错误计数；Bayer 顺序
结论需要结合 RAW 图样或后续 ISP 色彩结果。

## 12. 通过、失败和对外表述

### 12.1 通过条件

- II-0 至 II-D 的主路径门禁完成；
- 单一固定模式 API 与实际 30 fps 帧间隔一致；
- Controls 与寄存器/动态范围一致；
- 10 次、100 次短流通过，异常退出后能重开；
- runtime PM、clock、GPIO 和内存/引用没有持续泄漏；
- 原厂驱动和 minimal 路径保留且可回退；本轮不把重新执行同负载 A/B 作为主路径
  关闭条件，但不得把 A/B 写成已完成证据；
- 原始板端日志、hash 和代码版本完整归档。

### 12.2 不通过条件

以下任一情况都不能把阶段二写成“完成”：

- 只有代码、DTC、模块或 kernel 编译成功；
- 只看到 Subdev 注册，没有真实调用 `s_stream()`；
- 只使用原厂节点/原厂驱动得到 RAW 或 NV12；
- 运行 DT 中有两个同地址有效节点；
- 实际 DTB/TFTP hash 不明；
- 30 fps、Controls、PM 或错误路径缺少板端数据；
- 用阶段二短 RAW smoke 冒充阶段三 Media Graph/RKCIF/RKISP 验收。

## 13. 风险和第一版回退

| 风险 | 影响 | 第一版处理 | 回退 |
|---|---|---|---|
| 公共手册缺少推荐 mode 表 | 无法宣称独立推导 | 仅使用必要 [V] 值并逐项记账 | 回到 minimal 只验 I2C，或用原厂驱动 A/B |
| link/pixel/HBLANK 语义冲突 | 帧率或 Host 协商错误 | II-0 追踪 consumer，帧时间戳实测 | 冻结 control 为只读兼容值并记录限制 |
| selection target 不兼容 | RKCIF/RKISP 尺寸异常 | 追踪实际 caller 后冻结语义 | 先仅暴露完整 3864x2192，不宣称 4K crop |
| runtime PM 与 mutex 自锁 | STREAMON 卡死 | PM 边界外持锁，状态提交后置 | 临时关闭 autosuspend，保留显式 PM 引用 |
| stop I2C 失败导致状态不明 | 引用泄漏或无法重开 | 保留错误、确保 PM 引用守恒 | remove/reprobe；回到 minimal 复核硬件 |
| Host 图使 Sensor 问题难定位 | 出流失败根因混杂 | 先看 standby/MIPI 时钟和 Subdev trace | 阶段一 minimal 与原厂图分别 A/B |

| `0x311A` 不是官方唯一 ID | 型号证明边界有限 | 始终称厂商参考签名，叠加完整 mode 出流证据 | 不扩大 Chip ID 表述 |
